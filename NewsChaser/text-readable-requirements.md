# NewsChaser 内容与格式要求 v1

## 内容责任：逐事件展开

本期所选事件不设数量上限，但所有事件均需进入要求清单。每项使用稳定事件 ID 作为 scope，id 由事件 ID 加栏目名组成。各项独立核查：

| 栏目 | 实质要求 |
| --- | --- |
| 标题与摘要 | 中性概括本期已发生的事情；区分主张与事实。 |
| 时间、地点与参与方 | 写时间口径、发生地、人物/机构及身份；多地点时区分发生地与受影响地区。 |
| 起因与背景 | 有来源的触发因素及必要背景；当事方解释保留归属，不能把先后当因果。 |
| 经过 | 按时间顺序记录关键进展，不只重复摘要。 |
| 结果／当前状态 | 已确认的结果或进行中的状态，不强行给出结局。 |
| 影响 | 单独说明有来源的已观察变化，指出影响对象。结果句不能自动算作影响；若同一事实兼具两者作用，应明确受影响对象及变化。必要预测注明提出者、条件与不确定性，禁止智能体自行推演。 |
| 争议与未知 | 主要分歧、归属与证据状态；尚未获取回应不能改为没有回应。 |
| 后续节点 | 已公布日程、待公布结果及待决事项，不写建议或自行预测。 |
| 较上次变化 | 有历史时说明新增、状态变化或更正；无历史时由调用方明确本次未作历史对照。 |
| 来源与标签 | 关键事实附近有可点击引用；地区、主要领域与关联标签准确，稳定事件 ID 唯一。 |

未知或不适用时，保留调用方核查后写出的具体说明及必要影响，不能为了填栏自动断言“暂无影响”或“无争议”。重复摘要、泛称“影响重大”、只写栏目名或占位符均不满足内容要求。

全文另设内容项：时间范围与时区、核查截止点、筛选条件与排序标准、完整事件清单、两个索引、来源及覆盖限制。核对清单、索引与正文事件集合一致，不遗漏或重复。

## 格式约束：生成本期 format

- document_headings 固定包含：## 本期事件、## 地区索引、## 领域索引、## 事件正文、## 覆盖与核查限制。
- unit_level=3；sections 按本期所有事件逐项生成，heading 为该事件实际的完整三级标题行。事件标题不得重复，本期三级标题仅用于事件。
- 每项 required_markers 固定包含：**标签：**、**摘要：**、**时间、地点与参与方：**、**起因与背景：**、**经过：**、**结果／当前状态：**、**影响：**、**争议与未知：**、**后续节点：**、**较上次变化：**。
- 每个栏目用独立行，并在同一行开始写实质内容；后续允许扩展段落。不得合并“结果”与“影响”，不得只交付标题加两句概括。来源就近嵌入事实，不必额外重复来源栏目。

## 调用与交付门槛

1. 起草前读取本文件，按本次实际材料和用户要求展开具体约束。将每项内容责任转换为 content 中的 id、scope、requirement；不能只传原文或模板路径。
2. 事实核查完成后，将完整 original_text 与 output_requirements 一起冻结。调用时显式读取 ../TextReadable/AGENTS.md、workflow.md、checklist.md、interface.md、requirements.md，在当前任务中执行，output_mode=agent、max_rounds=3。每份报告最多 2 批。
3. 在本次产物 .cache/ 保存 original-text.md、output-requirements.json 和候选稿；这些属于已授权的本地产物。要求版本记录在 quality-review.md，不混入脚本输入对象。
4. 初稿缺少实质内容时由调用方回到来源核查。补充事实或缺口说明后明确新基准；不能要求 TextReadable 编造内容、预测或未知状态来凑齐字段。已有内容可无损调整格式，计入修改轮数。
5. 取回逐项 requirement_results，核对每个条目的原文与终稿位置、依据和状态；少一项也不能通过。所有适用内容与格式检查必须 pass，未查不能等同于不适用。
6. 对最终 report.md 运行 TextReadable/scripts/check_format.py，传入本次 output-requirements.json。记录命令结果与 sha256，失败则在预算内修改复查，不能宣布通过。脚本成功仍需内容覆盖审查。
7. 对话正文使用已审校版本；不得在返回时另写一个删栏摘要替代完整正文。确实超过容量时按完整章节或事件分批展示，说明剩余内容及完整文件位置。完整文件和逐批正文都必须保留适用要求。改动正文后原通过状态失效，按受影响范围复查，不增加预算。
8. 保持最终事实、专业或图片检查职责；无法通过时交付明确状态与缺口，不能为了合格删除要求。用户明确调整结构时由调用方记录新要求，再审校。
